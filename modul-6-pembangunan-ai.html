BAHAGIAN 01

Prompt Engineering

Cara bertanya supaya dapat kod yang berguna

Tugas yang sama, dua prompt

AI hanya tahu apa yang anda beritahu

LEMAH


buat api resit bayaran laravel
  • Versi Laravel? AI teka, selalunya versi lama
  • Model apa? AI cipta model dan kolum sendiri
  • Siapa boleh lihat resit? Tidak disebut, jadi tidak dikawal
  • Ujian? Tidak diminta, tidak diberi

KUAT


Konteks: Laravel 13, PHP 8.4, Sanctum. Sistem bayaran yuran.
Model Payment belongsTo Student dan Invoice.
InvoicePolicy::view() benarkan pemilik invois dan Bendahari.

Tugas: GET /api/v1/receipts/{payment} pulangkan reference,
nama pelajar, nombor invois dan amaun.

Kekangan:
- Pelajar hanya boleh lihat resit sendiri (guna InvoicePolicy)
- Ikut gaya controller sedia ada: final class, JsonResponse
- Jangan ubah bootstrap/app.php

Output: controller, baris route, ujian Pest untuk 200, 403, 401.
Tanya saya dahulu jika ada yang tidak jelas.
Tunjuk secara langsung dengan alat AI kelas: hantar kedua-dua prompt dalam sembang baru dan bandingkan. Biasanya prompt lemah menghasilkan controller tanpa sebarang semakan kebenaran, kerana peraturan "resit sendiri sahaja" tidak pernah disebut. Jawapan AI berbeza setiap kali, jadi bincang apa yang muncul, bukan apa yang dijangka.

Kerja bersama AI

Pelan dahulu, kod kemudian

  1. Minta pelan: "Senaraikan fail yang akan diubah dan kenapa. Jangan tulis kod lagi."
  2. Betulkan pelan: buang yang tidak perlu, tambah kekangan yang terlepas
  3. Satu langkah setiap kali: satu fail atau satu method, jalankan ujian, kemudian langkah seterusnya
  4. Tampal ralat sebenar: output penuh php artisan test, bukan "tak jalan"

Kenapa?

Membetulkan pelan lima baris jauh lebih murah daripada membaca 200 baris kod yang salah arah.

Langkah kecil bermakna setiap perubahan boleh diuji dengan ujian Modul 5 sebelum perubahan seterusnya.

Kitaran ini sama seperti TDD dalam Modul 5: langkah kecil, sahkan, kemudian teruskan. Untuk alat agent (yang boleh menjalankan arahan sendiri), langkah 1 dan 2 paling penting: luluskan pelan sebelum ia mengubah fail.

Prompt semakan

Minta bukti, bukan pendapat


Semak kod ini sebagai senior Laravel developer.

Konteks: Laravel 13, Sanctum. config/app.php timezone UTC;
semua pengguna di Malaysia (UTC+8).
Pelajar hanya boleh lihat bayaran sendiri; Bendahari boleh
lihat semua. InvoicePolicy::view() sudah wujud.

Cari: logic error, security gap, query berlebihan.

Untuk setiap isu beri:
1. baris
2. kenapa ia salah, dengan contoh input
3. cara membuktikannya (ujian atau arahan)
4. pembaikan paling kecil

Jangan ulas gaya penulisan atau nama pemboleh ubah.

[tampal kod]
  • Peraturan akses dalam konteks: tanpanya AI tidak tahu Aisyah tidak boleh lihat resit Badrul
  • Zon masa: maklumat yang tiada dalam kod tetapi mengubah makna today()
  • Cara membuktikan: memaksa setiap dapatan boleh disemak. Dapatan tanpa bukti ialah tekaan
  • Jangan ulas gaya: elak 20 komen kosmetik yang menenggelamkan satu lubang keselamatan
Pull request untuk disemak

Resit pelajar dan laporan harian Bendahari

app/Http/Controllers/Api/V1/ReceiptController.php


namespace App\Http\Controllers\Api\V1;

use App\Http\Controllers\Controller;
use App\Models\Payment;
use Illuminate\Http\JsonResponse;

final class ReceiptController extends Controller
{
    public function show(Payment $payment): JsonResponse
    {
        return response()->json([
            'reference' => $payment->reference,
            'student' => $payment->student->name,
            'invoice' => $payment->invoice->number,
            'amount' => $payment->amount,
        ]);
    }

    public function today(): JsonResponse
    {
        $payments = Payment::whereDate('paid_at', today())->get();

        return response()->json($payments->map(fn (Payment $p) => [
            'reference' => $p->reference,
            'student' => $p->student->name,
            'amount' => $p->amount,
        ]));
    }
}

routes/api.php (dalam kumpulan auth:sanctum)


Route::get('receipts/{payment}', [ReceiptController::class, 'show']);
Route::get('reports/payments-today', [ReceiptController::class, 'today'])
    ->middleware('can:view-bursary-reports');

AI menyemak, meja membuktikan

  1. Hantar ReceiptController dengan prompt semakan tadi
  2. Salin setiap dapatan AI ke satu jadual: betul, salah, atau belum pasti
  3. Untuk setiap dapatan "betul", buktikan dengan satu ujian yang merah pada kod ini

Bukti siap

Jadual dapatan meja, dan sekurang-kurangnya satu ujian merah yang membuktikan satu masalah.

Petunjuk: Sanctum::actingAs() (Modul 5), $this->expectsDatabaseQueryCount(), Carbon::setTestNow().

Setiap meja guna satu alat AI. Bandingkan jadual antara meja: alat atau prompt yang berbeza menghasilkan dapatan berbeza, dan itulah sebabnya setiap dapatan mesti dibuktikan. Dapatan "salah" yang lazim: mendakwa SQL injection pada whereDate() (Eloquent guna parameter binding), atau mass assignment (tiada create/update dalam kod ini).

Pembaikan

Tiga baris berubah

app/Http/Controllers/Api/V1/ReceiptController.php


namespace App\Http\Controllers\Api\V1;

use App\Http\Controllers\Controller;
use App\Models\Payment;
use Illuminate\Http\JsonResponse;
use Illuminate\Support\Facades\Gate;

final class ReceiptController extends Controller
{
    public function show(Payment $payment): JsonResponse
    {
        Gate::authorize('view', $payment->invoice);

        return response()->json([ /* sama seperti tadi */ ]);
    }

    public function today(): JsonResponse
    {
        $day = now('Asia/Kuala_Lumpur');

        $payments = Payment::with('student')
            ->whereBetween('paid_at', [
                $day->copy()->startOfDay()->utc(),
                $day->copy()->endOfDay()->utc(),
            ])
            ->get();

        return response()->json($payments->map(/* sama seperti tadi */));
    }
}

Semak ujian yang dijana

Ujian yang tidak pernah merah tidak menguji apa-apa

AI boleh tulis 10 ujian dalam 10 saat. Semuanya hijau. Tetapi adakah ia akan menangkap pepijat?

Rosakkan kod dengan sengaja, satu demi satu, dan lihat ujian mana yang merah:

RosakkanUjian yang mesti merah
Buang Gate::authorize()Pelajar lain dapat 403
Buang with('student')expectsDatabaseQueryCount(2)
Tukar now('Asia/Kuala_Lumpur') kepada now()Bayaran 7:30 pagi muncul dalam laporan

Tanda ujian AI yang lemah

  • Hanya assertOk(), tiada semakan isi
  • Nilai jangkaan disalin dari output kod, bukan dari peraturan
  • Mock class yang sedang diuji
  • Tiada kes yang sepatutnya gagal: 403, 422, 409
Teknik ini dipanggil mutation testing apabila dibuat secara automatik; di sini kita buat dengan tangan. Ia prinsip yang sama seperti "lihat merah dahulu" dalam TDD Modul 5.

Sebelum composer require

  • Buka packagist.org: pakej wujud?
  • Siapa maintainer? Vendor laravel/ hanya untuk pakej rasmi
  • Jumlah muat turun dan tarikh release terakhir
  • Repo GitHub wujud dan aktif
  • Selepas pasang: composer audit
Output composer di slide ini diambil daripada projek Laravel 13 sebenar. composer audit menyemak pakej yang dipasang terhadap pangkalan data kerentanan yang diketahui; ia tidak dapat mengesan pakej berniat jahat yang baru didaftarkan, sebab itu semakan Packagist tetap perlu.
Data

Apa yang tidak boleh ditampal ke dalam prompt

Jangan tampal

  • Isi .env: APP_KEY, kata laluan DB, kunci FPX, client secret Passport
  • Token Sanctum atau token pengguna
  • Data pelajar sebenar: nama, no. matrik, no. kad pengenalan, emel
  • Log production (Modul 5: log boleh mengandungi data peribadi)
  • Dump pangkalan data

Tampal ini sebagai ganti

  • .env.example, tanpa nilai sebenar
  • Data daripada factory: Aisyah, INV0000001
  • Mesej ralat dan stack trace, selepas membuang nilai peribadi
  • Skema: fail migration jadual berkaitan
Ejen AI dalam editor boleh membaca fail dalam projek, termasuk .env. Semak tetapan alat anda untuk mengecualikan fail rahsia, dan ikut dasar ICT universiti tentang penggunaan alat AI.
Jangan beri tafsiran undang-undang. Arahkan peserta kepada dasar ICT dan pegawai perlindungan data di jabatan masing-masing untuk soalan undang-undang.

  5. Commit message ditulis oleh anda: apa dan kenapa

Setiap fail: Status, Context (kenapa perlu memilih, dengan bukti), Decision (pilihan dan peraturan yang boleh disemak). Pilihan: Consequences, Revisit when.

Bila tulis ADR?

  • Keputusan itu mahal untuk diterbalikkan
  • Seseorang akan bertanya "kenapa tidak guna X?"
  • Ia mengelak kesilapan yang pernah berlaku

Peraturan

  • Nama fail NNNN-slug.md, nombor tidak diguna semula
  • Status: proposed → accepted, tarikh
  • ADR accepted tidak ditulis semula. Keputusan berubah = ADR baru yang supersede (menggantikan) ADR lama
Lima ADR ini ialah keputusan yang sudah kita buat sepanjang kursus, cuma belum ditulis. Tanya peserta: dalam projek anda, di mana keputusan seperti ini disimpan sekarang? Jawapan biasa: dalam kepala seorang senior, atau dalam mesej WhatsApp.
Contoh ADR (Architecture Decision Record)

Pepijat zon masa, ditulis sekali untuk selamanya

docs/adr/0004-utc-storage-malaysia-day.md


# 0004 — Store times in UTC, count days in Malaysian time

**Status:** accepted, 2026-11-27

## Context

`config/app.php` uses UTC. Every student and the Bursary are
in Malaysia (UTC+8). The daily report built on `today()`
missed a 7:30 am payment (Modul 6: count=0). A scheduled task
without `timezone()` ran at 8:00 am, not midnight (Modul 4).

## Decision

**The app timezone stays UTC. Days, months and due dates are
computed in Malaysian time, then converted to a UTC range.**

- Start from `now('Asia/Kuala_Lumpur')`; no `today()` or
  `whereDate()` on time columns.
- Every scheduled task that follows local time has
  `->timezone('Asia/Kuala_Lumpur')`.
- Every daily report has a test at 7:30 am Malaysian time
  using `Carbon::setTestNow()`.

## Revisit when

The system has to serve users outside UTC+8.
  • Context menyimpan bukti: nombor sebenar dari kursus, bukan pendapat
  • Decision ditulis sebagai peraturan yang penyemak boleh semak satu demi satu
  • Peraturan ketiga ialah ujian: ADR menyatakan apa, ujian (Modul 5) membuktikannya
  • Revisit when ialah syarat yang boleh diukur, bukan "jika keperluan berubah"
Developer baru, atau AI, yang membaca fail ini tidak akan menulis today() dalam laporan lagi.
UTC (Coordinated Universal Time) sudah dikembangkan di Bahagian Code Review. Tarikh accepted ialah hari terakhir kursus, sebagai contoh. Templat 0000-template.md mempunyai bahagian Status, Context, Decision, Consequences, Revisit when dan Not yet; dua yang terakhir hanya diisi jika ada sesuatu untuk dikatakan.

Langkah seterusnya

Minggu depan, dalam projek anda sendiri

  1. Pilih satu aliran kritikal (bayaran, log masuk, laporan). Tulis satu feature test untuknya
  2. Pasang Laravel Debugbar atau Telescope di mesin anda. Cari satu N+1

  4. Pindahkan satu kerja lambat (emel, eksport) ke queue
