Queues & Jobs

Job dispatch, queue workers, failed jobs dan retry strategy

Masalah

Puan Siti tunggu 3.76 saat untuk satu laporan

app/Http/Controllers/Api/V1/CollectionExportController.php


namespace App\Http\Controllers\Api\V1;

use App\Http\Controllers\Controller;
use App\Models\Payment;
use Illuminate\Http\JsonResponse;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\Storage;

final class CollectionExportController extends Controller
{
    public function store(Request $request): JsonResponse
    {
        $year = $request->integer('year');
        $path = "reports/kutipan-{$year}.csv";
        Storage::makeDirectory('reports');
        $handle = fopen(Storage::path($path), 'w');
        fputcsv($handle, ['rujukan', 'invois', 'kaedah', 'amaun', 'tarikh']);

        Payment::with('invoice')->whereYear('paid_at', $year)->lazyById(1000)
            ->each(fn (Payment $p) => fputcsv($handle, [
                $p->reference, $p->invoice->number, $p->method->value, $p->amount, $p->paid_at,
            ]));
        fclose($handle);

        return response()->json(['path' => $path], 201);
    }
}

Kenapa ia masalah

Kerja berat dalam request vs dalam queue

Pengguna: 3.76 s menunggu, dan jika pelayar ditutup, kerja mungkin terhenti separuh jalan.

Pelayan: bilangan proses PHP terhad. Jika 10 Bendahari eksport serentak, pelajar yang mahu membayar terpaksa beratur.

Tekan anak panah untuk dedahkan baris kedua. Nombor 0.038 s dan 3 s diukur selepas eksport dipindahkan ke job (dua slide lagi). Queue = senarai kerja yang menunggu; worker = proses berasingan yang mengambil kerja dari senarai itu dan menjalankannya.
Langkah 1 · cipta job

php artisan make:job ExportCollectionReport

app/Jobs/ExportCollectionReport.php


namespace App\Jobs;

use App\Mail\CollectionReportReady;
use App\Models\Payment;
use App\Models\User;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Queue\Queueable;
use Illuminate\Support\Facades\Mail;
use Illuminate\Support\Facades\Storage;

final class ExportCollectionReport implements ShouldQueue
{
    use Queueable;

    public function __construct(public User $requestedBy, public int $year) {}

    public function handle(): void
    {
        // kod eksport dari slide "Puan Siti tunggu 3.76 saat untuk satu laporan",
        // tanpa diubah, kecuali $year menjadi $this->year

        Mail::to($this->requestedBy->email)->send(new CollectionReportReady($path));
    }
}
  • ShouldQueue: tanda "jangan jalankan sekarang, masukkan ke queue". Interface yang sama seperti listener Modul 1
  • Queueable: trait yang memberi dispatch(), onQueue(), delay() dan simpan model sebagai id
  • Constructor = data yang job perlukan. Ia disimpan, kemudian dibaca semula oleh worker
  • handle() = kerja sebenar. Kod eksport dipindah tanpa diubah
  • Siap: hantar emel dengan fail dilampirkan
Job tiada $request. Semua yang diperlukan mesti dihantar melalui constructor: pengguna dan tahun.
CollectionReportReady ialah Mailable biasa dengan attachments() => [Attachment::fromStorage($this->path)]. Kodnya tidak ditunjukkan kerana Mailable bukan fokus modul ini.

Di dalam queue

Apa yang sebenarnya disimpan?


mysql> SELECT queue, attempts FROM jobs;
queue    attempts
default  0

payload.displayName = "App\Jobs\ExportCollectionReport"
payload.data.command =
  O:31:"App\Jobs\ExportCollectionReport":2:{
    s:11:"requestedBy";O:45:"Illuminate\Contracts\Database\ModelIdentifier":5:{
        s:5:"class";s:15:"App\Models\User";s:2:"id";i:3; ... }
    s:4:"year";i:2026;

Model User disimpan sebagai ModelIdentifier: nama class + id 3 sahaja. Worker ambil semula rekod segar dari DB sebelum handle().

Akibatnya: jika rekod dipadam sebelum worker sempat, job gagal. Dan nilai yang bukan model (seperti year) disimpan apa adanya, jadi jangan hantar objek besar atau sambungan fail.

Payload diambil terus dari jadual jobs (lajur payload ialah JSON; data.command ialah objek PHP yang diserialize). Ini dari trait Queueable, yang termasuk SerializesModels. Baris "..." memendekkan medan relations, connection dan collectionClass.

Bila job gagal

Sistem kewangan sedang down

app/Jobs/SyncPaymentToFinance.php


namespace App\Jobs;

use App\Models\Payment;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Queue\Queueable;
use Illuminate\Support\Facades\Http;

final class SyncPaymentToFinance implements ShouldQueue
{
    use Queueable;

    public int $tries = 4;

    public array $backoff = [10, 30, 60];

    public function __construct(public Payment $payment) {}

    public function handle(): void
    {
        Http::timeout(5)
            ->post(config('services.finance.url').'/payments', [
                'reference' => $this->payment->reference,
                'amount' => $this->payment->amount,
            ])
            ->throw();
    }
}

config/services.php (tambah)


'finance' => [
    'url' => env('FINANCE_URL'),
],
  • Setiap bayaran perlu dihantar ke sistem kewangan universiti (pelanggan Passport dalam Modul 3)
  • $tries = 4: cuba paling banyak 4 kali
  • $backoff = [10, 30, 60]: tunggu 10 s sebelum cubaan ke-2, 30 s sebelum ke-3, 60 s sebelum ke-4
  • ->throw(): jadikan status 4xx/5xx satu exception. Tanpanya, 503 dianggap "berjaya" dan job tidak dicuba semula
Http ialah HTTP client Laravel (pembalut Guzzle). Dalam ujian, FINANCE_URL menghala ke pelayan stub yang pulangkan 503 {"message":"Service Unavailable"}. Untuk produksi, backoff lebih panjang seperti [60, 300, 900] lebih munasabah.

Retry yang selamat

Bagaimana jika cubaan pertama sebenarnya berjaya?

Senario

Sistem kewangan terima bayaran dan simpan, tetapi response lambat. Http::timeout(5) tamat, job dikira gagal dan dicuba semula. Bayaran yang sama kini direkod dua kali.

Penyelesaian: idempotent

Hantar kunci unik yang sama setiap cubaan: reference bayaran. Penerima simpan sekali sahaja untuk setiap reference, dan pulangkan berjaya untuk cubaan berulang.

Idempotent (hasil sama walau diulang): soalan pertama untuk setiap job yang ada $tries lebih dari 1. "Jika job ini berjalan dua kali, apa yang rosak?"
Konsep yang sama seperti kunci unik dan locking untuk double payment dalam Modul 2. Job yang menulis ke DB sendiri boleh guna updateOrCreate() atau unique index untuk jadi idempotent.

Empat worker memproses 2.6 kali lebih banyak job daripada satu. Tambah worker biasanya lebih berkesan daripada tukar driver.

Cara tambah worker: mesin anda

Setiap proses queue:work ialah satu worker. Buka 4 terminal dan jalankan arahan yang sama dalam setiap satu:

php artisan queue:work

Keempat-empatnya mengambil job dari queue yang sama; satu job hanya diambil oleh satu worker.

Cara tambah worker: pelayan

Jangan buka terminal; ia mati bila anda log keluar. Biar Supervisor menjalankannya:

numprocs=4

Konfigurasi Supervisor penuh ada dua slide lagi.

Diukur pada mesin trainer: NoopJob dengan handle() kosong, queue:work --stop-when-empty --sleep=0, MySQL 8 dan Redis tempatan. Setiap worker memproses kira-kira 2,000 job. Ukuran 4 worker dijalankan sebagai 4 proses queue:work serentak, sama seperti 4 terminal. Bilangan worker yang sesuai bergantung pada CPU dan jenis job: mula dengan bilangan teras CPU, ukur, kemudian laraskan. Nombor akan berbeza pada pelayan sebenar; yang penting ialah cara mengukur.

Laravel Scheduler dan automasi berasaskan cron

Masalah

Siapa yang tekan butang setiap pagi?

Hari ini

Pegawai Bendahari jalankan query invois lewat 7 hari, salin emel ke Outlook, hantar satu demi satu. Cuti? Tiada peringatan.

Matlamat

Setiap hari jam 8:00 pagi, sistem cari invois yang lewat tepat 7 hari dan masukkan satu emel peringatan untuk setiap invois ke queue.

Dua langkah: (1) tulis command artisan yang buat kerja itu sekali, (2) beritahu scheduler bila ia perlu berjalan.
Langkah 1 · command

php artisan make:command SendFeeReminders

app/Console/Commands/SendFeeReminders.php


namespace App\Console\Commands;

use App\Mail\FeeReminder;
use App\Models\Invoice;
use Illuminate\Console\Attributes\Description;
use Illuminate\Console\Attributes\Signature;
use Illuminate\Console\Command;
use Illuminate\Support\Facades\Mail;

#[Signature('invoices:send-reminders')]
#[Description('Hantar peringatan untuk invois yang lewat 7 hari')]
final class SendFeeReminders extends Command
{
    public function handle(): int
    {
        $invoices = Invoice::overdue()
            ->whereDate('due_date', today()->subDays(7))
            ->with('student');

        $count = 0;
        $invoices->lazyById(500)->each(function (Invoice $invoice) use (&$count) {
            Mail::to($invoice->student->email)->queue(new FeeReminder($invoice));
            $count++;
        });

        $this->info("{$count} peringatan dimasukkan ke queue.");

        return self::SUCCESS;
    }
}
  • #[Signature] = nama command. Laravel 13 menjana stub dengan attribute PHP, seperti #[Fillable] dalam Modul 3
  • overdue(): scope dari Bahagian Advanced Eloquent, Modul 2
  • Mail::...->queue(), bukan send(): command selesai dalam setengah saat; 278 emel dihantar oleh worker
  • use (&$count): closure menambah pemboleh ubah di luarnya
  • self::SUCCESS = kod keluar 0, supaya cron tahu ia berjaya
FeeReminder ialah Mailable biasa dengan subjek "Peringatan: invois INV… lewat 7 hari". Command stub Laravel 13 dijana dengan #[Signature('app:send-fee-reminders')] dan #[Description('Command description')]; kedua-duanya ditukar.

Perangkap · zon masa

Kenapa 8:00 pagi tertulis 0 0 * * *?


$ php artisan schedule:list
 0 0 * * *  php artisan invoices:send-reminders ......... Next Due: 17 hours from now
 0 0 * * *  php artisan sanctum:prune-expired --hours=24  Next Due: 17 hours from now
 0 0 * * *  php artisan queue:prune-failed --hours=168 .. Next Due: 17 hours from now

$ php artisan schedule:list --timezone=Asia/Kuala_Lumpur
 0 8 * * *  php artisan invoices:send-reminders ......... Next Due: 17 hours from now

config/app.php guna 'timezone' => 'UTC' (Coordinated Universal Time). 8:00 pagi Malaysia = 00:00 UTC. Jadual betul; paparannya dalam UTC.

Tetapi daily() tanpa timezone() berjalan 00:00 UTC = 8:00 pagi Malaysia, bukan tengah malam. Sentiasa nyatakan timezone() untuk tugas yang bergantung pada waktu tempatan.

Output sebenar pada 22 November 2026, kira-kira 2:48 petang waktu Malaysia. Untuk prune token dan failed jobs, waktu tepat tidak penting, jadi daily() tanpa timezone() tidak mengapa.

Dengan Redis, worker ambil job sebelum transaksi commit, jadi bayaran belum wujud. Dengan database driver, baris job berada dalam transaksi yang sama, jadi pepijat ini tersembunyi sehingga hari anda tukar driver. Event ShouldDispatchAfterCommit menunggu commit.

Observer pattern

Subjek memberitahu, pemerhati bertindak

  • Observer pattern: satu objek (subjek) memberitahu senarai pemerhati bila keadaannya berubah. Subjek tidak tahu apa yang pemerhati buat
  • Event & listener ialah bentuk umum: anda tentukan bila event dihantar
  • Model observer ialah bentuk khusus Eloquent: Laravel hantar event sendiri bila model dicipta, dikemas kini atau dipadam
Method observerDipanggil bila
creating / createdSebelum / selepas INSERT
updating / updatedSebelum / selepas UPDATE
saving / savedKedua-dua insert dan update
deleting / deletedSebelum / selepas DELETE
Keperluan audit: setiap kali amaun invois diubah, catat nilai lama dan baru. Tidak kira dari controller mana ia diubah.
Model observer

InvoiceObserver dengan #[ObservedBy]

app/Observers/InvoiceObserver.php


namespace App\Observers;

use App\Models\Invoice;
use Illuminate\Support\Facades\Log;

final class InvoiceObserver
{
    public function updated(Invoice $invoice): void
    {
        if ($invoice->wasChanged('amount')) {
            Log::warning('Amaun invois diubah', [
                'invoice' => $invoice->number,
                'dari' => $invoice->getOriginal('amount'),
                'kepada' => $invoice->amount,
            ]);
        }
    }
}

app/Models/Invoice.php (tambah)


use App\Observers\InvoiceObserver;
use Illuminate\Database\Eloquent\Attributes\ObservedBy;

#[ObservedBy(InvoiceObserver::class)]
class Invoice extends Model
{
    // ... seperti Modul 2
}
  • #[ObservedBy]: attribute PHP yang mendaftarkan observer pada model. Tiada service provider
  • wasChanged('amount'): hanya log bila amaun sebenarnya berubah
  • Dalam updated(), getOriginal() masih memegang nilai lama
Baris 10 ialah semakan wasChanged, 11 ialah log, 12–14 ialah data log. Observer biasa berjalan serta-merta dalam request yang sama; tambah ShouldQueue pada observer jika kerjanya berat.

BAHAGIAN 05

Broadcasting

Event masa nyata ke pelayar (overview)

Dashboard Bendahari

Tanya setiap 5 saat, atau diberitahu?

WebSocket: sambungan yang kekal terbuka antara pelayar dan pelayan, supaya pelayan boleh menghantar mesej tanpa diminta. Laravel tidak memegang sambungan ini sendiri; ia menyerahkan mesej kepada pelayan WebSocket.

Tekan anak panah untuk dedahkan baris kedua. 720 = 3,600 saat / 5 saat. Bahagian ini overview: kita lihat bahagian Laravel (event dan payload) yang boleh diuji tanpa pelayan WebSocket.
Pilihan pelayan

Siapa yang memegang sambungan?

JenisCatatan
Laravel ReverbDihoskan sendiri, pakej rasmi LaravelDipasang melalui php artisan install:broadcasting; berjalan dengan php artisan reverb:start
Pusher ChannelsPerkhidmatan berbayar (SaaS, Software as a Service)Tiada pelayan untuk diurus; had sambungan ikut pelan
SoketiDihoskan sendiri, sumber terbukaBercakap protokol Pusher, jadi Laravel guna driver pusher yang dihalakan ke pelayan sendiri

Ketiga-tiganya guna protokol Pusher, jadi kod Laravel dan kod pelayar (Laravel Echo) hampir sama. Yang berubah ialah .env.

Untuk UTM: data bayaran kekal dalam rangkaian sendiri dengan Reverb atau Soketi. Pusher paling cepat untuk mula.

Tiada pelayan WebSocket diuji dalam kursus ini; maklumat ini daripada dokumentasi Laravel (Broadcasting) dan Soketi. install:broadcasting bertanya secara interaktif sama ada mahu pasang Reverb; ia juga mendaftar routes/channels.php dalam bootstrap/app.php. Untuk ujian tanpa pelayan, BROADCAST_CONNECTION=log menulis setiap broadcast ke storage/logs/laravel.log.
Bahagian Laravel

Event yang sama, kini juga dihantar ke pelayar

app/Events/PaymentReceived.php


namespace App\Events;

use App\Models\Payment;
use Illuminate\Broadcasting\PrivateChannel;
use Illuminate\Contracts\Broadcasting\ShouldBroadcast;
use Illuminate\Contracts\Events\ShouldDispatchAfterCommit;
use Illuminate\Foundation\Events\Dispatchable;

final class PaymentReceived implements ShouldDispatchAfterCommit, ShouldBroadcast
{
    use Dispatchable;

    public function __construct(public Payment $payment) {}

    public function broadcastOn(): array
    {
        return [new PrivateChannel('bursary')];
    }

    public function broadcastAs(): string
    {
        return 'payment.received';
    }
}

routes/channels.php


use App\Models\User;
use Illuminate\Support\Facades\Broadcast;

Broadcast::channel('bursary', fn (User $user) => $user->isBursary());
  • ShouldBroadcast: selain listener biasa, event ini juga dihantar ke pelayan WebSocket
  • PrivateChannel('bursary'): hanya pengguna yang lulus semakan dalam channels.php boleh mendengar. Pelajar tidak boleh
  • broadcastAs(): nama event yang pelayar dengar
  • Broadcast juga melalui queue: worker menunjukkan App\Events\PaymentReceived ... DONE
