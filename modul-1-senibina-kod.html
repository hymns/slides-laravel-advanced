Sistem Bayaran Yuran Pelajar

Pelajar membayar invois yuran secara dalam talian.

  • Jenis invois: yuran semester, asrama, denda perpustakaan
  • Bayar selepas tarikh akhir → penalti lewat: semester 5%, asrama 2%, denda 0%
  • Kaedah bayaran: FPX, kad, e-wallet, kaunter Bendahari
  • Selepas bayaran: invois ditanda berbayar, resit dihantar melalui emel
  • Bayaran dibuat dari web, app mobile (API) dan import penyata kaunter (Artisan)
Domain ini sengaja dipilih kerana peserta (staf IT UTM) sudah kenal prosesnya. Semua contoh SOLID, Service Layer, Repository dan Container dalam modul ini guna domain yang sama.

public function store(Request $request)
{
    $request->validate([
        'invoice_id' => 'required|exists:invoices,id',
        'method'     => 'required|in:fpx,card,ewallet',
    ]);
    $invoice = Invoice::find($request->invoice_id);
    if ($invoice->paid_at) {
        return back()->withErrors(['invoice_id' => 'Invois sudah dibayar.']);
    }
    $amount = $invoice->amount;
    if (now()->gt($invoice->due_date)) {
        if ($invoice->type == 'semester') { $amount = $amount * 1.05; }
        elseif ($invoice->type == 'hostel') { $amount = $amount * 1.02; }
    }
    if ($request->input('method') == 'fpx') {
        $ref = (new FpxClient(env('FPX_KEY')))->pay($invoice->number, $amount);
    } elseif ($request->input('method') == 'card') {
        $ref = (new CardClient(env('CARD_KEY')))->charge($amount);
    } else { $ref = (new EWalletClient(env('EWALLET_KEY')))->debit($amount); }

    $payment = Payment::create($request->all()
        + ['student_id' => auth()->user()->student->id, 'amount' => $amount, 'reference' => $ref]);
    $invoice->update(['paid_at' => now()]);
    Mail::to(auth()->user())->send(new PaymentReceipt($payment));
    return redirect()->route('payments.show', $payment);
}

Diagnosis

Apa masalahnya?

Susah diuji

Nak uji kiraan penalti, kena hantar HTTP request, ada DB, dan FPX betul-betul dicaj.

Tidak boleh guna semula

App mobile dan import penyata kaunter perlu salin-tampal logik yang sama → 3 versi berbeza dalam 6 bulan.

Isu tersembunyi

$request->all() → mass assignment. env() di luar config → null bila config:cache.

Terlalu banyak sebab berubah

Kadar penalti berubah? Bank tukar API FPX? Kaedah bayaran baru? Semua sentuh fail yang sama.

Emel blok response

Pelajar tunggu pelayan emel hantar resit sebelum nampak halaman "bayaran berjaya".

Race condition

Dua klik serentak boleh bayar invois yang sama dua kali. (Kita selesaikan dalam Modul 2.)

S · Single Responsibility Principle (SRP)

“Satu sebab untuk berubah”

Robert C. Martin: “A module should be responsible to one, and only one, actor.”

Bukan “satu method” — tetapi satu pihak yang meminta perubahan.

Fat controller tadi melayan 6 pihak:

Pasukan UX (validasi) → StorePaymentRequest
Bendahari (kadar penalti) → LatePenaltyCalculator
Integrasi bank (FPX / kad) → PaymentProcessor
Aliran bayaran → PaymentService
Komunikasi (emel resit) → SendPaymentReceipt
Web / API (format response) → PaymentController
Ujian cepat: cuba terangkan class anda dalam satu ayat tanpa perkataan “dan”.

final class LatePenaltyCalculator
{
    public function for(Invoice $invoice, CarbonInterface $today): float
    {
        if ($today->lte($invoice->due_date)) {
            return 0.0;
        }

        return match ($invoice->type) {
            FeeType::Semester    => $invoice->amount * 0.05,
            FeeType::Hostel      => $invoice->amount * 0.02,
            FeeType::LibraryFine => 0.0,
        };
    }
}

Satu tempat, satu pihak (Bendahari), mudah diuji tanpa HTTP/DB.

Kenapa jadikan default

  • Nak tingkah laku berbeza? Tulis class baru yang implement interface yang sama (slide seterusnya), bukan extend class sedia ada.
  • Boleh ubah class dengan selamat: tiada subclass tersembunyi yang bergantung pada dalamannya.
  • Dalam test, kita mock interface, bukan class final (Bahagian 04).
Interface tak boleh final, dan enum sudah final secara automatik. final ialah pilihan, bukan wajib: dalam kursus ini ia default untuk class aplikasi. Kalau peserta tanya "kalau saya perlu extend nanti?": buang final bila sebab itu muncul. Lebih mudah buang final daripada betulkan subclass yang dah bergantung pada dalaman class.

app/Payments/PaymentProcessor.php


namespace App\Payments;

use App\Enums\PaymentMethod;
use App\Models\Invoice;
use LogicException;

final class PaymentProcessor
{
    public function __construct(private iterable $gateways) {}

    public function charge(Invoice $invoice, PaymentMethod $method, float $amount): string
    {
        foreach ($this->gateways as $gateway) {
            if ($gateway->supports($method)) {
                return $gateway->charge($invoice, $amount);
            }
        }

        throw new LogicException("Kaedah bayaran tidak disokong: {$method->value}");
    }
}

L · Liskov Substitution Principle (LSP)

Implementasi tak boleh “mungkir janji”

Semester berikutnya, Bendahari minta ciri refund. Kita tambah refund() pada interface:


interface PaymentGateway
{
    public function supports(PaymentMethod $method): bool;
    public function charge(Invoice $invoice, float $amount): string;
    public function refund(Payment $payment): void;   // baru
}
// Method baru → SEMUA gateway (Fpx, Card, EWallet, Counter) wajib ada refund()

final class CardGateway implements PaymentGateway
{
    // ...supports() dan charge() seperti slide sebelum
    public function refund(Payment $payment): void
    {
        Http::withToken(config('services.card.key'))
            ->post(config('services.card.url').'/refund', [
                'reference' => $payment->reference])
            ->throw();   // wang dipulangkan ke kad pelajar
    }
}

final class CounterGateway implements PaymentGateway
{
    // ...supports() dan charge() seperti slide sebelum
    public function refund(Payment $payment): void
    {
        // bayaran tunai: tiada API untuk pulangkan wang
        throw new RuntimeException('Refund kaunter mesti diproses manual');
    }
}

Tanda-tanda langgar LSP

  • Method yang throw “not supported”
  • Method kosong yang tak buat apa-apa
  • if ($x instanceof Something) dalam pemanggil
  • Return type lebih longgar (null bila parent janji objek)

Pembetulan

Bayaran kaunter memang tidak boleh di-refund secara automatik. Pisahkan kontrak:

PaymentGateway + Refundable. CounterGateway hanya implement yang pertama.

→ Pembetulan LSP selalunya membawa kepada ISP (Interface Segregation Principle).

L · Liskov Substitution Principle (LSP)

Kenapa RuntimeException?

Kod yang memanggil refund()


final class RefundService
{
    // Terima apa-apa objek yang implement PaymentGateway
    public function __construct(private PaymentGateway $gateway) {}

    public function refund(Payment $payment): void
    {
        $this->gateway->refund($payment);
        $payment->update(['status' => 'refunded']);
    }
}

// Bayaran kad: refund() memang pulangkan wang
$service = new RefundService(new CardGateway());
$service->refund($cardPayment);      // OK

// Bayaran di kaunter Bendahari
$service = new RefundService(new CounterGateway());
$service->refund($counterPayment);   // RuntimeException!
  1. RefundService hanya kenal interface PaymentGateway, jadi ia percaya refund() akan pulangkan wang
  2. Dengan CardGateway, janji itu ditepati: API kad pulangkan wang
  3. Dengan CounterGateway, refund() throw. Status bayaran tak sempat dikemas kini, pelajar nampak HTTP 500
PHP semak signature, bukan janji. CounterGateway lulus implements PaymentGateway kerana nama method dan jenis parameter sama. Tapi tingkah lakunya berbeza.
Kod refund() tak salah. Untuk "selamatkan" ia, pemanggil terpaksa tulis if ($gateway instanceof CounterGateway). Itu tanda langgar LSP yang kedua.
Sengaja guna "new" di sini. Dalam Bahagian 04, Service Container yang akan pilih dan suntik objek ini secara automatik, tapi masalah LSP tetap sama. Tekankan: ujian unit dengan CardGateway lulus; bug hanya muncul bila bayaran kaunter di-refund.

Siapa buat apa

Pembahagian tanggungjawab

Controller

Bahasa: HTTP

  • Terima request yang sudah divalidasi
  • Tukar ke DTO (Data Transfer Object)
  • Panggil service
  • Pilih response (view / JSON / redirect)
  • Query DB
  • Kira penalti

Bahasa: use case bisnes

  • Sempadan transaksi DB
  • Dispatch domain event
  • request(), session()
  • Return Response

  • Query yang dinamakan dengan jelas
  • Persist & ambil data
  • Hantar emel
  • Tahu tentang HTTP

final class PaymentService
{
    public function __construct(
        private InvoiceRepository $invoices,
        private LatePenaltyCalculator $penalties,
        private PaymentProcessor $processor,
    ) {}

    public function pay(Student $student, PaymentData $data): Payment
    {
        $invoice = $this->invoices->findOrFail($data->invoiceId);
        if ($invoice->paid_at !== null) {
            throw InvoiceAlreadyPaidException::for($invoice);
        }
        $amount = $invoice->amount + $this->penalties->for($invoice, now());
        // panggilan ke bank: di luar transaksi DB
        $reference = $this->processor->charge($invoice, $data->method, $amount);
        return DB::transaction(function () use ($invoice, $student, $data, $amount, $reference) {
            $payment = $this->invoices->recordPayment($invoice, [
                'student_id' => $student->id, 'method' => $data->method,
                'amount' => $amount, 'reference' => $reference, 'paid_at' => now(),
            ]);
            PaymentReceived::dispatch($payment);
            return $payment;
        });
    }
}
1) Dependency di constructor: tiga keperluan service, semuanya jelas. 2) Invois sudah dibayar = throw domain exception, bukan return redirect. 3) Penalti dikira oleh LatePenaltyCalculator (slide SRP). 4) Caj bank DI LUAR transaksi: jangan pegang transaksi DB sambil tunggu bank yang mungkin ambil 10 saat. 5) Rekod bayaran + tanda invois berbayar dalam satu transaksi. 6) Event: listener hanya jalan selepas commit (slide seterusnya).

Panduan

Do & don't Service Layer

Lakukan

  • Namakan ikut use case: pay, refund, waive
  • Terima DTO (Data Transfer Object) / model / scalar (nilai tunggal: int, string, float, bool) — bukan Request
  • Return model, DTO atau void
  • Throw domain exception untuk peraturan bisnes yang gagal
  • Inject dependency melalui constructor
  • Pecahkan bila service melebihi ~7 dependency

Elakkan

  • request(), auth(), session() dalam service
  • Return redirect() / response()
  • “God service”: UserService 2,000 baris
  • Service yang hanya forward ke model tanpa logik (anemic pass-through)
  • Static method — susah di-mock
  • Service panggil controller

Alternatif yang popular: Action class (satu class per use case, cth. PayInvoice::handle()). Prinsipnya sama — pilih satu konvensyen untuk pasukan.

Contoh tiga jenis parameter: pay(Student $student, PaymentData $data) guna model + DTO; waive(int $invoiceId, string $reason) guna scalar. Semua boleh dipanggil dari web, API atau Artisan; Request hanya wujud dalam HTTP.

namespace App\Repositories\Eloquent;

use App\Models\{Invoice, Payment, Student};
use App\Repositories\Contracts\InvoiceRepository;
use Illuminate\Database\Eloquent\Collection;

final class EloquentInvoiceRepository implements InvoiceRepository
{
    public function findOrFail(int $id): Invoice
    {
        return Invoice::findOrFail($id);
    }

    public function outstandingFor(Student $student): Collection
    {
        return $student->invoices()
            ->whereNull('paid_at')
            ->orderBy('due_date')
            ->get();
    }

    public function recordPayment(Invoice $invoice, array $attributes): Payment
    {
        $payment = $invoice->payments()->create($attributes);
        $invoice->update(['paid_at' => $payment->paid_at]);

        return $payment;
    }
}

}
  1. $invoice->payments()->create($attributes) (slide sebelum) cipta satu Payment baru.
  2. Laravel isi invoice_id sendiri melalui relationship payments() dalam model Invoice.
  3. Payment::$fillable tentukan kunci mana dalam $attributes dibenarkan masuk ke DB.
Kunci array mesti sama dengan nama kolum dan ada dalam $fillable. Kalau tidak, medan itu diabaikan tanpa ralat.
Peranan $casts dalam aliran ini: dalam $attributes, 'method' ialah enum PaymentMethod::Fpx (dari PaymentData), bukan string.

app/Repositories/Cached/CachedInvoiceRepository.php


namespace App\Repositories\Cached;

use App\Models\{Invoice, Payment, Student};
use App\Repositories\Contracts\InvoiceRepository;
use Illuminate\Contracts\Cache\Repository as Cache;
use Illuminate\Database\Eloquent\Collection;

final class CachedInvoiceRepository implements InvoiceRepository
{
    public function __construct(private InvoiceRepository $inner, private Cache $cache) {}

    public function findOrFail(int $id): Invoice
    {
        return $this->inner->findOrFail($id);
    }

    public function outstandingFor(Student $student): Collection
    {
        return $this->cache->remember(
            "invoices:outstanding:{$student->id}",
            now()->addMinutes(10),
            fn () => $this->inner->outstandingFor($student),
        );
    }

    public function recordPayment(Invoice $invoice, array $attributes): Payment
    {
        $payment = $this->inner->recordPayment($invoice, $attributes);
        $this->cache->forget("invoices:outstanding:{$invoice->student_id}");

        return $payment;
    }
}

Debat jujur

Perlu ke Repository dengan Eloquent?

Berbaloi bila…

  • Query kompleks digunakan di banyak tempat
  • Data datang dari pelbagai sumber (DB + API luar + cache)
  • Mahu unit test service tanpa DB
  • Pasukan besar — kontrak jelas antara lapisan
  • Perlu decorator (cache, audit log, multi-tenant scope)

Beban bila…

  • CRUD ringkas — repo cuma forward ke Model::find()
  • Method bocor Eloquent: return Builder atau terima closure query
  • BaseRepository generik dengan 40 method
  • Alasan “nanti nak tukar ORM (Object-Relational Mapping)” — jarang berlaku
Pendekatan pragmatik: mula dengan query scopes & service. Perkenalkan repository untuk agregat yang kompleks atau kritikal, bukan semua model secara automatik.

namespace App\Providers;

use App\Payments\{CardGateway, CounterGateway, EWalletGateway,
    FpxGateway, PaymentProcessor, SandboxGateway};
use App\Repositories\Contracts\InvoiceRepository;
use App\Repositories\Eloquent\EloquentInvoiceRepository;
use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    /** Binding mudah: interface => class */
    public array $bindings = [
        InvoiceRepository::class => EloquentInvoiceRepository::class,
    ];

    public function register(): void
    {
        // Jawapan slide Strategy: siapa bina senarai gateway?
        $this->app->singleton(PaymentProcessor::class, fn ($app) =>
            new PaymentProcessor($app->environment('production')
                ? [$app->make(FpxGateway::class), $app->make(CardGateway::class),
                   $app->make(EWalletGateway::class), $app->make(CounterGateway::class)]
                : [new SandboxGateway()]
            )
        );
    }
}
AppServiceProvider sudah wujud dan sudah aktif dalam setiap projek Laravel baru. Tak perlu cipta atau daftar apa-apa: terus tambah binding di sini.

register() vs boot()

register() — hanya binding. Jangan resolve service lain di sini.

boot() — selepas semua provider didaftar: event, macro, observer, Gate.

Sengaja guna AppServiceProvider sahaja. Projek besar boleh pecahkan ke provider berasingan (php artisan make:provider), tapi itu tidak perlu untuk kursus ini.
